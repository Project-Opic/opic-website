一、部署形态与目录

容器化模式 = 8 项基础设施全部以容器交付（数据面 Pigsty 形态见 116 号 §三决策 1，用于生产；本模式用于 DEV 与 minimal 档）：

宿主 192.168.3.200
├── 统一入口  opic-traefik        :18880(web) :19443(websecure) :18887(dashboard)
├── 数据面    opic-pg (16)        127.0.0.1:15432（回环排障口，容器网 opic-net 内 5432）
│             opic-redis (8)      127.0.0.1:26379（同上）
├── 身份面    opic-zitadel        经网关 auth.192.168.3.200.nip.io:18880
│             opic-zitadel-login  （login 前端，仅容器网内 :3000）
│             opic-casdoor        :18001
├── 中间件    opic-nats           :14222(client) :8222(monitor)
│             opic-temporal(+pg+ui) :7233(gRPC) :8233(UI)
└── 镜像仓    harbor(安装器自管)   :18700
  • 所有栈通过外部 Docker 网络 opic-net 互联；数据目录统一在 /opt/opic/。
  • 部署根目录：/opt/opic-deploy-step1（独立于既有 /opt/opic-deploy 域中心目录）。
  • 端口规划依据：宿主 80/443 被系统 nginx 占用、8080 被 kube-router 占用、8000/4222/5432/16379/18090-18115/18443/8880-8881/8086 被既有容器（go-admin-kit、zt-traefik、oc-redis 等）占用 → 全部让开。

二、快速开始（3 条命令）

cd /opt/opic-deploy-step1
bash bin/install-step1.sh                 # F0~F8 全量（含 Harbor）
bash bin/install-step1.sh --no-registry   # 跳过 Harbor（离线拿不到安装包时）
bash bin/verify-step1.sh                  # 八项健康门禁（可随时重跑）

install-step1.sh 幂等可重跑：已存在的 .env 不会被覆盖，已健康的栈会秒过。

四、配置源（.env 要点）

  • 唯一配置源是 .env（从 .env.example 生成），口令只存在于该文件；configs/ 下无任何口令。
  • ZITADEL_DOMAIN 与 ZITADEL_EXTERNALPORT 必须与浏览器地址栏一致（OIDC issuer 由它构成）。DEV 用 auth.192.168.3.200.nip.io:18880（nip.io 泛解析到 192.168.3.200）；若内网无外网 DNS，在各访问机的 /etc/hosts 加 192.168.3.200 auth.192.168.3.200.nip.io。
  • 口令复杂度：ZITADEL/Harbor 校验口令策略（大写+小写+数字+符号），gen-env.sh 生成 Op1- 前缀格式自动合规；手工填入口令时须自行满足。
  • 镜像源：ZITADEL 官方镜像在 ghcr.io 且 tag 带 v 前缀（ghcr.io/zitadel/zitadel:v4.19.3），docker hub 无 v 前缀且部分国内 mirror 不收录——DEV .env 已指向 ghcr。Casdoor 无可核验版本 tag 源，默认 latest，首装后建议回填锁定。

六、首次部署实测记录与已知坑

2026-10-01 在 192.168.3.200 实测过程中发现并已修复/规避的问题（新环境部署遇到同类症状可直接对号入座）：

  1. compose healthcheck 不支持 environment 键：Redis 栈最初把 REDISCLI_AUTH 写在 healthcheck 内 → additional properties 'environment' not allowed。已改为 service 级 environment + healthcheck 里 redis-cli ping。
  2. 空端口变量会绑随机端口："${REDIS_PORT:-}:6379" 在变量为空时绑定随机宿主端口。已改为固定回环默认值（如 127.0.0.1:26379:6379）。
  3. 宿主端口冲突：16379 被既有 oc-redis 占用 → Redis 换 26379；80/443/8080/8000/4222/5432 均被占用 → 全部高位让开（见 §一端口表）。
  4. 共享 docker.sock 的发现污染：宿主上 go-admin-kit 等容器自带 traefik labels，会被新 Traefik 收编 → 加 --providers.docker.constraints=LabelRegex(\opic.stack`,`.+`)，只发现带 opic.stack` 标签的 OPIC 容器。
  5. traefik healthcheck 404：scratch 镜像无 curl/wget，traefik healthcheck 需显式传入口点与地址：--ping=true --ping.entrypoint=web --entrypoints.web.address=:80。
  6. ZITADEL 镜像源：docker hub 镜像在部分国内 mirror 不在白名单 → 用 ghcr.io（tag 带 v 前缀）。
  7. ZITADEL 口令复杂度：首实例初始化会校验 admin 口令复杂度（PasswordComplexityPolicy.HasUpper），纯小写 hex 口令导致 setup 失败 → 口令生成改为 Op1- 前缀格式。
  8. ZITADEL healthcheck 死锁：traefik 会过滤非 healthy 容器，而 zitadel ready 拨测经网关的外部域名 → 路由不注册 ↔ 不 healthy 互等。栈内刻意不设 healthcheck，就绪判定由 post-install 网关门禁承担。
  9. bootstrap 卷属主：Docker 命名卷默认 root，zitadel（uid 1000）写 login-client PAT 报 permission denied → 栈内加一次性 init-perms 容器 chown。
  10. 跨容器 traefik label：Traefik 的 service 只指向 label 所在容器 —— login 路由必须挂在 login 容器上（挂 API 容器上会 502）。
  11. Casdoor 双坑：dbName 只从 conf/app.conf 读（env DSN 只管连接），缺了报 zero-length delimited identifier；--createDatabase=true 需 CREATEDB 权限，库已由 database 栈建好时不带该参数。
  12. NATS max_streams：不接受服务器级配置（2.14 报 unknown field），属账号级限额。
  13. Temporal 版本天花板：temporalio/auto-setup 上游最高 1.29.x（docker-compose 仓已归档，无 1.30+ 镜像），全仓统一 1.29.0；镜像在受限网络可经任一可出网机器 docker save → scp → docker load 迁移。admin-tools 无 1.29.0，用 1.30.4（向后兼容）。
  14. 跨架构镜像搬运：从 Apple Silicon 机器 docker save 导出的默认是 arm64 变体，搬到 x86 宿主容器起不来（仅日志一行 platform mismatch）→ 导出前必须 docker pull --platform linux/amd64。

七、与生产形态（Pigsty）的切换

容器化模式是 minimal/DEV 形态。切生产时（116 号 §三决策 1）：

  1. 数据面改由 Pigsty 主机级安装（PG HA + Redis 模块），stacks/database、stacks/redis 停用；
  2. ZITADEL/Casdoor/Temporal 的数据库连接指向 Pigsty 实例（改 .env 的 host/端口与 SSL 模式）；
  3. Traefik 关闭 api.insecure，启用 TLS（证书由 O-CRT 域供给）；
  4. Temporal 库并入 Pigsty 统一实例（temporal/temporal_visibility 由 Pigsty 建库授权）。

三、凭据与密钥管理

  • 唯一口令源是 /opt/opic-deploy-step1/.env（权限 600）。丢失即失去全部凭据。
  • ZITADEL_MASTERKEY（32 字符）是最高优先级密钥：ZITADEL 用它加密库内全部密钥材料，丢失 = ZITADEL 既有数据不可用。备份要求：.env 加密存放（如 age/gpg），至少一份异地。
  • 改口令流程：改 .env → docker compose up -d（重建受影响容器）。ZITADEL masterkey 不可换（换了等于销毁数据）；应用口令（PG/Redis/NATS 等）在容器重建后即生效，PG 已建角色的口令需同步 ALTER ROLE。

建议最小巡检 cron（示例，每天 02:00 备份 + 每小时探针）：

0 2 * * * docker exec opic-pg pg_dumpall -U postgres | gzip > /backup/pg-$(date +\%F).sql.gz
0 * * * * /opt/opic-deploy-step1/bin/verify-step1.sh || echo "step1 门禁异常" | wall

五、升级与回滚

# 升级某组件：改 .env 的 *_IMAGE_TAG → 拉新镜像 → 逆序停 → 正序起
vim .env                                    # 如 TRAEFIK_IMAGE_TAG=v3.7.13
cd stacks/traefik && docker compose pull
cd ../.. && bash bin/teardown-step1.sh && bash bin/install-step1.sh
  • ZITADEL 升级：小版本直接升；跨大版本先读官方迁移公告（schema 由其自管）。
  • 回滚：.env 改回旧 tag 后同样流程；数据目录不删（bind mount），旧版本可直接挂回。

七、安全基线（对外/上生产前必须逐项核对）

  1. Casdoor admin/123 首登改密；ZITADEL admin 口令确认已按复杂度设置并轮换。
  2. Traefik 关闭 api.insecure（dashboard 走受控路由+鉴权）。
  3. Temporal gRPC/UI 默认无认证——只允许内网，对外必须经网关加认证（或启用 mTLS）。
  4. NATS monitor 8222 不暴露公网；跨机时客户端与监控启用 TLS。
  5. PG/Redis 回环排障口（15432/26379）只在本机使用；生产建议注释 compose 的 ports 段。
  6. .env 600 且不进 git；.env 备份加密。
  7. Traefik 发现约束 opic.stack 标签必须保留——否则会收编宿主上其他项目的 traefik 路由（实测教训，见部署指南 §六）。

十、生产形态（Pigsty）运维增补

生产形态按《OPIC 基础设施生产部署方案》（工程内嵌副本 《OPIC 基础设施生产部署》，主件在 opic-ontology 工作区 output/118 号）执行：数据面（PG HA + Redis）由 Pigsty 主机级托管，应用面仍是本仓 compose。本章只讲与容器化模式不同的运维动作；通用纪律（§一~§九）继续适用。

10.1 架构速览与端口语义

应用节点(node-4)                      数据节点(node-1/2/3)
Traefik :443(TLS) ──┐                 Patroni(:8008) + etcd(:2379)
ZITADEL/Casdoor/…   ├─► haproxy VIP ── :5433 → primary（读写）
NATS/Temporal       │    (node-1/2/3)  :5434 → replicas（只读/负载均衡）
Harbor :8443 ───────┘                 PGBackRest → node-3 存储 → 异地
Pigsty INFRA(node-3): Grafana :3000 / Prometheus :9090（仅内网）
  • 5433 = 读写（primary），5434 = 只读（replicas 轮询）——应用连接串按读写分离分别配置；VIP 漂移不影响这两端口语义。
  • 应用栈的 .env.prod 中库地址一律写 VIP:5433（不直连节点 IP，failover 才无感）。

10.2 日常巡检（数据面）

# 集群角色与复制状态（任一数据节点）
patronictl -c /etc/patroni/patroni.yml list
# haproxy 后端健康（node-4 或管理机）
curl -s http://node-1:7000/stats; csv  # 或访问 haproxy 统计页
# 复制延迟（primary 上）
psql -h <vip> -p 5433 -U postgres -c "SELECT client_addr, state, sync_state, replay_lag FROM pg_stat_replication;"
# 备份有效性
pgbackrest --stanza=pgsql info        # 最新备份须为 available，无 error
# Redis
redis-cli -h <redis-vip> PING && redis-cli -h <redis-vip> INFO replication | grep -E "role|master_link"

巡检最小集（进 crontab，每小时）：复制延迟 >10s、WAL 目录堆积、磁盘 >85%、pgbackrest info 有 error、 Patroni 成员非 running。

10.3 主备切换与故障处置

# 计划内切换（低峰窗口；switchover 自带回切点记录）
patronictl -c /etc/patroni/patroni.yml switchover opic-pg --leader node-1 --candidate node-2
# 主库真故障：Patroni 自动 failover（etcd 仲裁），无需人工；事后
patronictl list                        # 确认新 primary
pgbackrest --stanza=pgsql backup       # 尽快补一次全量基备
# 旧主回归：自动降级为 standby 并跟进新主（pg_rewind）；若失败
patronictl reinit opic-pg <旧主>       # ⚠ 以新主数据为基准重建

纪律：切换演练每季度一次（118 号 §五）；failover 后 10 分钟内完成 pgbackrest backup，否则视为未收口。

10.4 备份恢复（PGBackRest）

# 手动全量/增量
pgbackrest --stanza=pgsql --type=full backup
pgbackrest --stanza=pgsql --type=incr backup
# 恢复演练（每月；恢复到临时目录验证，不覆盖生产）
pgbackrest --stanza=pgsql --set=<最新全量名> \
  --delta --target-action=promote --type=time "--target=2026-10-01 12:00:00+08" \
  --pg1-path=/data/pgsql/restore-check restore
# 恢复后校验：库数、行数抽样、ZITADEL instance 表存在

RPO ≤5 分钟 / RTO ≤30 分钟（118 号 §五）；演练记录归档 ops 台账，连续两月未演练按红线上报。

10.5 证书与安全基线轮换

  • 通配符证书（Traefik + Harbor 同一张）：新证书放 node-4 /opt/opic/certs/ → docker compose restart traefik → Harbor 侧更新 harbor.yml 后 cd harbor-installer && docker compose restart nginx；到期前 30 天告警。
  • api.insecure=false 为生产硬约束——巡检项：curl -s http://node-4:8088/api/http/routers 必须拒绝连接。
  • pg_hba.conf 变更走变更单：改 postgres_conf（Pigsty 声明式）→ patronictl reload → pg_hba_file_rules 审计无 trust/宽网段。

10.6 升级流程（生产）

对象顺序回退锚点

PG 小版本先 pgbackrest full → switchover 到备 → 升旧主 → 再切回（滚动）PITR
Pigsty 版本读 release note → 测试环境预演 → 生产按 node 逐台 playbook按库 dump + 旧版重装

  • VIP:5433 读写 / :5434 只读 均通；应用栈均连 VIP（非节点 IP）

  • ZITADEL healthz/login、Casdoor、NATS /jsz、Temporal cluster health、Harbor /api/v2.0/health 全绿

一、一句话结论

生产形态 = Pigsty 主机级托管数据面（PG 高可用 + Redis，Ansible 幂等安装）＋ docker compose 托管应用面（ZITADEL/Casdoor/NATS/Temporal/Harbor）＋ Traefik TLS 统一入口（域名 + 证书）；边界判据不变（116 号）：有持久状态且要主机级 HA → Pigsty，无状态或容器化优先 → compose。全流程映射 115 号 S 序，安装编排为 P0~P9（§四）。

六、安全基线（生产版，上线前逐项核对）

  1. 防火墙最小端口：node-1/2/3 仅放行节点间网段（5433/5434/8008 patroni/2379-2380 etcd/9100-9101 exporter/22 管理网）；node-4 对外仅 80/443/8443，22 限管理网；Pigsty Grafana(3000)/Prometheus(9090) 仅内网。

  3. Traefik api.insecure=false（DEV 坑位结论直接继承）；dashboard 如需开放走 BasicAuth + 内网 ACL。
  4. 全站 TLS：五域名证书链校验入月度巡检；证书到期前 30 天告警（O-MON 或 cron）。
  5. SSH：key-only、禁 root 密码、fail2ban；管理操作留 X-Trace-Id 习惯（平台规则第 8 条审计头）。
  6. .env.prod 与 masterkey：age 加密存放于堡垒/密码库；严禁入 git（.gitignore 已排除 .env*）。

七、监控与告警衔接

  • 采集面：Pigsty INFRA 自带 Prometheus/Grafana（PG/PGPool/Redis/节点 exporter），保留为本机采集（116 号 §三决策 5）。
  • 聚合面：O-MON（第二步）联邦采集上述 Prometheus；第一步期间用 Pigsty 内置告警最小集：复制延迟 >10s、WAL 堆积、磁盘 >85%、连接数 >80%、backup 失败、证书到期不足 30 天。
  • 门禁巡检：verify 脚本（生产版）进 crontab 每小时，异常 wall + 消息通道。
