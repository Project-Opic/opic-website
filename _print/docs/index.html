1 - 平台简介

OPIC 开放智能算力平台

OPIC 是一套以本体论（Ontology）驱动的智算 + MaaS 一体化平台：23 个能力域构成完整的语义层，覆盖从物理算力入网到 AI 应用消费的全链路。

三个差异化主张

  1. 本体论驱动的需求工程——需求是机器可校验的语义体系：每域一份《需求规格说明书》与《编制说明》，受 927 项自动审核、一致性扫描（130 条跨域引用零断链）、第九部分 13 项自检三道闸门约束，需求基线以 SHA-256 清单冻结。
  2. 第 3 层可整体替换——全部开源依赖被隔离在依赖层，替换引擎不触发需求变更；替换暴露语义缺口才走需求变更。
  3. 业界对标 20 条必备全部达标（2026-09 刷新口径，含 Batch 推理、结构化输出、护栏独立 API、缓存计价分列、模型退役承诺）。

5 - 安全与合规

安全与合规

凭据谱系八位置

平台内每一类凭据在谱系上有唯一位置与暴露上界：证书可导出（O-CRT）、集群 SSH 零持久化（O-CLC）、OS 使能零凭据借道（O-OSC）、镜像令牌只在内存流转、AI 令牌一次显示（O-APF）、共享库凭据（O-DBS）等。审计账本只增不改；安全事件与调用审计两流不合并（粒度、保留策略、消费者不同）。

内容合规（法定义务）

生成内容标识三要素（属性信息 / 提供者编码 / 内容编号）对标 GB 45438-2025（2025-09-01 施行）；备案状态机对接外部监管；上线前置闸门把合规从「事后审计」变成「发布阻断」；护栏档（GuardrailProfile）让同一策略按 ID 复用于任意接入点，未挂载接入点使用显式默认档。

零信任与机密计算

授权判定：Casbin RBAC 优先 → 拒绝则查 IdP → 任一通过即允许；判定与执行分离，阻断在消费方。机密计算部署档 + 节点 TEE 能力回源 + attestation 归第 3 层 + HYOK 密钥权威在租户侧。

6 - 计量与运营方法论

计量与运营方法论

判据：「事实与原语在本域，方法与参数在外部」——平台输出「多少钱、花在哪、谁承担、用得如何」四类事实；方法论在其上自由定义。

计量事实（平台承载）

成本记录按六维聚合维度记账；分摊规则原语（ratio 类型 + 比例归一强校验，未命中显式落 unallocated 黑洞不隐藏）；账单可复现（任一账单可从计量事实重放）；多轴计价：路径轴（online / batch / cached）× 承诺轴（standard / priority / reserved / spot），被抢占时段计价豁免；缓存 tokens 分列 + 让利显式；SLA 补偿凭证入账（与违约判定、SLO 定义三方闭环）。

TCO 五要素归集（六维 → 五要素）

TCO 要素归集来源口径
① 算力计算资源维度按分配台账占用事实折算
② 存储存储维度按存储实例利用率
③ 网络网络维度参数面 + 业务面流量
④ 运维人力与工单维度外部工单系统按中心归集
⑤ 电力与机房能耗维度机房计量事实

60:40 双权重分摊（配置法）

在分摊规则原语上配置两条 ratio 规则即可表达（如业务线 60% 按用量 / 部门 40% 按配额）；权重调整有审计、不追溯已封账账单。

ROI 6:4 测算模板（外部计算）

ROI(周期) = (业务收益归集值 × 6) / (平台 TCO 归集值 × 4)
业务收益归集值 = Σ(挂靠应用调用量 × 单位收益系数)     ← 取数：成本账单（按应用维度）
平台 TCO 归集值  = 五要素合计                          ← 取数：成本账单 / 利用率报告

决策阈值建议：ROI ≥ 1.5 扩容线、1.0~1.5 维持线、< 1.0 专项复盘线。平台「建议零执行」——所有建议由人确认。

7 - 业界对标

业界对标（2026-09 刷新口径）

20 条「缺则不合格」必备能力：达标 20/20。 15 条经典必备（多租户与配额、Token 计量与缓存分列、流式与函数调用声明、gang 调度、算力切分语义、内容标识、模型退役承诺、SLA 治理、A/B 与数据飞轮、RAG 引用溯源等）+ 2025H2 新必备 5 项（Batch API、Prompt caching 计价、结构化输出/约束解码、护栏独立 API、模型退役公开承诺）。

  • 本体化需求工程（机器可校验的需求基线在业界罕见）

2026 风向兼容性

Agent 双协议（MCP 入 LF + A2A）｜计价多轴化｜推理架构换代（PD 分离 / KV 感知路由契约位已预留）｜K8s 底座定型（DRA GA / Kueue 默认化——直接吸收）。

8 - 技术选型评估

技术选型评估：Temporal 与 NATS

结论：不新建能力中心；NATS 单归属平台底座域（O-SYS），Temporal 双归属应用域（业务语义）+ 平台底座域（底座接入）。

  • NATS = 事件总线的第 3 层可替换实现（Core NATS 发布订阅 / JetStream 持久化）；各中心只依赖事件契约（subject 命名、审计头透传、统一信封），不得直绑 NATS API。
  • Temporal = 持久工作流执行引擎。工作流业务语义已在应用域（WorkflowDefinition，执行明细显式「不落本域」——Temporal 恰是该声明的域外承载）；引擎平台接入语义（集群编目、namespace / task-queue 治理、跨中心访问、审计）归平台底座域。每中心一个 task queue、各自 Worker，跨中心编排走网关/事件。
  • 不新建中心的判据：新域门槛是「新的业务事实领地」；引擎可整体替换是第 3 层纪律。
  • 首批落点：联邦部署编排、批量推理作业完成窗口、智能体会话恢复、交付任务桥接补偿（Temporal）；事件总线实现、告警投递、变更通知（NATS）。
  • 工程落地：部署与适配代码归 platform-base-center；Worker SDK 集成归 application-center；技术底座脚手架新增消息与工作流封装模块。

六、首次部署实测记录与已知坑

2026-10-01 在 192.168.3.200 实测过程中发现并已修复/规避的问题（新环境部署遇到同类症状可直接对号入座）：

  1. compose healthcheck 不支持 environment 键：Redis 栈最初把 REDISCLI_AUTH 写在 healthcheck 内 → additional properties 'environment' not allowed。已改为 service 级 environment + healthcheck 里 redis-cli ping。
  2. 空端口变量会绑随机端口："${REDIS_PORT:-}:6379" 在变量为空时绑定随机宿主端口。已改为固定回环默认值（如 127.0.0.1:26379:6379）。
  3. 宿主端口冲突：16379 被既有 oc-redis 占用 → Redis 换 26379；80/443/8080/8000/4222/5432 均被占用 → 全部高位让开（见 §一端口表）。
  4. 共享 docker.sock 的发现污染：宿主上 go-admin-kit 等容器自带 traefik labels，会被新 Traefik 收编 → 加 --providers.docker.constraints=LabelRegex(\opic.stack`,`.+`)，只发现带 opic.stack` 标签的 OPIC 容器。
  5. traefik healthcheck 404：scratch 镜像无 curl/wget，traefik healthcheck 需显式传入口点与地址：--ping=true --ping.entrypoint=web --entrypoints.web.address=:80。
  6. ZITADEL 镜像源：docker hub 镜像在部分国内 mirror 不在白名单 → 用 ghcr.io（tag 带 v 前缀）。
  7. ZITADEL 口令复杂度：首实例初始化会校验 admin 口令复杂度（PasswordComplexityPolicy.HasUpper），纯小写 hex 口令导致 setup 失败 → 口令生成改为 Op1- 前缀格式。
  8. ZITADEL healthcheck 死锁：traefik 会过滤非 healthy 容器，而 zitadel ready 拨测经网关的外部域名 → 路由不注册 ↔ 不 healthy 互等。栈内刻意不设 healthcheck，就绪判定由 post-install 网关门禁承担。
  9. bootstrap 卷属主：Docker 命名卷默认 root，zitadel（uid 1000）写 login-client PAT 报 permission denied → 栈内加一次性 init-perms 容器 chown。
  10. 跨容器 traefik label：Traefik 的 service 只指向 label 所在容器 —— login 路由必须挂在 login 容器上（挂 API 容器上会 502）。
  11. Casdoor 双坑：dbName 只从 conf/app.conf 读（env DSN 只管连接），缺了报 zero-length delimited identifier；--createDatabase=true 需 CREATEDB 权限，库已由 database 栈建好时不带该参数。
  12. NATS max_streams：不接受服务器级配置（2.14 报 unknown field），属账号级限额。
  13. Temporal 版本天花板：temporalio/auto-setup 上游最高 1.29.x（docker-compose 仓已归档，无 1.30+ 镜像），全仓统一 1.29.0；镜像在受限网络可经任一可出网机器 docker save → scp → docker load 迁移。admin-tools 无 1.29.0，用 1.30.4（向后兼容）。
  14. 跨架构镜像搬运：从 Apple Silicon 机器 docker save 导出的默认是 arm64 变体，搬到 x86 宿主容器起不来（仅日志一行 platform mismatch）→ 导出前必须 docker pull --platform linux/amd64。

七、与生产形态（Pigsty）的切换

容器化模式是 minimal/DEV 形态。切生产时（116 号 §三决策 1）：

  1. 数据面改由 Pigsty 主机级安装（PG HA + Redis 模块），stacks/database、stacks/redis 停用；
  2. ZITADEL/Casdoor/Temporal 的数据库连接指向 Pigsty 实例（改 .env 的 host/端口与 SSL 模式）；
  3. Traefik 关闭 api.insecure，启用 TLS（证书由 O-CRT 域供给）；
  4. Temporal 库并入 Pigsty 统一实例（temporal/temporal_visibility 由 Pigsty 建库授权）。

登录与 SSO

Q1：管理员 SSO 登录报"系统中未找到用户"？ 登录名写错。ZITADEL 实例域名是 zitadel.auth.opic-ai.ccoe.tech，不是文档示例的 zitadel.localhost。且管理控制台 SSO 应使用底座管理员账号：登录名 admin（口令见 /opt/opic-prod/.env 的 ZITADEL_TECHBASE_ADMIN_PASSWORD），它会映射本地 admin 并保留管理权限。zitadel-admin@... 是 ZITADEL 平台自身的实例管理员，登录成功也只会开通普通业务账号。

Q2：ZITADEL 登录报"无法为用户创建会话"？ 登录 UI 对密码校验失败的通用提示——口令不对。API 侧可用 POST /v2/sessions 验证口令（注意该接口必须带任意 Bearer 头，否则报 “auth header missing”）。

Q3：Casdoor 登录页只有"Sign in with Face ID"，无法输密码？ 应用配置被初始化成了仅 FaceID。修 casdoor 库 application 表：enable_password=t、signin_methods=[{"name":"Password",...}]，改后 docker restart opic-casdoor。

Q4：SSO 回调 401 “access token invalid”？ 三层都可能，按序排查：① casdoor 应用 expire_in_hours=0（token 签发即过期）→ 设 168；② 应用 cert 字段必须为裸名（如 cert-built-in，带 owner 前缀会拼成三段报错）；③ 客户端代码 userinfo discovery 误用了另一个 IdP 的配置（多 IdP 共用 pkg 时高发）。

Q5：ZITADEL 授权后 404（http://域名:443/ui/v2/login/...）？ https 端口收到明文 http。修两处：compose 的 LoginV2 URL 改 https://域名（无端口）；存量实例还须 PUT /v2/features/instance 更新 loginV2.baseUri（带 required:true，否则 v2 特性被关掉落到 v1 路径）。

接口与数据库

Q6：接口报 SQLSTATE 42601 “syntax error at or near ")""？ 空集合拼了 IN ()。动态 IN 列表前必须判空（无角色用户查待办即此坑），空时改按其他条件过滤。

Q7：保存/更新接口 404，但 GET 正常？ 后端漏注册对应 method 的路由（如只注册了 POST 而前端用 PUT）。gin 缺路由返回 404 而非 405；补路由时注意更新语义要从路径参数或 body 取 id，否则更新会落进 INSERT 分支报"编码已存在”。

Q8：接口返回 200 但前端拿到空数据？ 响应没包 OPIC 信封。axios 拦截器只认 returnInfo.returnCode='SUC0000' 并取 data 字段——裸 JSON/错误响应会被静默吞掉。统一用 common.OKJSON/FailJSON。

Q9：gorm Raw 查询数字字段类型断言失败？ PG smallint→int16、int→int64、numeric→float64。取值助手 service.Int() 已兼容，勿直接 .(int)。

部署与基础设施

Q10：本地构建的镜像服务器跑不起来？ Apple Silicon 产出 arm64 镜像。生产一律服务器侧构建（make deploy-prod 已内置 --network host，同时解决构建期 DNS 脏条目）。

Q11：容器内解析公司域名到 127.0.0.1？ 宿主 /etc/hosts 把 *.opic-ai.ccoe.tech 指向 127.0.0.1，Docker DNS 转发会继承。compose 给相关服务加 extra_hosts: 域名=host-gateway；https 自签证书再加 CA 挂载 + SSL_CERT_FILE。

Q12：docker compose 改了镜像/配置不生效？ docker compose up -d 只重建配置变化的容器；改镜像必须确认镜像 ID 变了（构建缓存可能命中旧层）。restart 不会换镜像。

Q13：Pigsty 监控（VictoriaMetrics）加了抓取目标不生效？ Pigsty 的 prometheus.yml 以 YAML 文档结束符 ... 结尾——追加内容必须在 ... 之前，否则解析失败、热加载被拒（旧配置保留）。YAML 合法性先本地校验。

Q14：vmetrics/grafana 等是 docker 还是系统服务？ Pigsty 全部为 systemd 服务（vmetrics:8428 / vmalert:8880 / grafana:3000 / alertmanager / node_exporter / pg_exporter），非容器。Grafana 面板放 /etc/dashboards/（Pigsty provider 扫描路径）自动加载。

前端

Q15：接口 200 但页面拿到的对象字段是 null 导致白屏？ Go 空 slice 序列化为 null 而非 []。返回给前端的列表字段必须 make([]T, 0) 初始化。

Q16：按钮样式被全局主题覆盖（内联样式无效）？ 品牌 CSS 用了 !important。覆盖它需要同优先级写法（相同属性选择器 + 置于文件末尾），或新增专用类。

AI 助理

Q17：助理回复固定话术（不走大模型）？ LLM 调用失败自动降级规则引擎。docker logs | grep assistant 看降级原因；管理台「AI 模型配置」对账号点「测试」。kimi-for-coding 仅允许默认温度（账号温度须为 0 即不发送）。

Q18：新增模型账号后 AI 助理选择器不显示？ 账号需「启用」；前端模型选择持久化在 localStorage，切换账号后刷新页面即可见。
