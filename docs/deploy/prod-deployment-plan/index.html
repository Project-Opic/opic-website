一、一句话结论

生产形态 = Pigsty 主机级托管数据面（PG 高可用 + Redis，Ansible 幂等安装）＋ docker compose 托管应用面（ZITADEL/Casdoor/NATS/Temporal/Harbor）＋ Traefik TLS 统一入口（域名 + 证书）；边界判据不变（116 号）：有持久状态且要主机级 HA → Pigsty，无状态或容器化优先 → compose。全流程映射 115 号 S 序，安装编排为 P0~P9（§四）。

二、参考拓扑与节点规划

拓扑是参考基准而非硬性要求——Pigsty 支持单机到任意规模，节点数按现场资源伸缩，角色边界（数据面/应用面分离）必须保持。

2.1 节点角色

节点角色承载数量（最小/推荐）
node-1PG 主Pigsty PGSQL（primary）＋ etcd ＋ PGBackRest1/1
node-2PG 备Pigsty PGSQL（replica，流复制）＋ etcd1/1~2
node-3基础设施etcd（仲裁）＋ Pigsty INFRA（Prometheus/Grafana 采集面）＋ 备份存储挂载（NFS/对象网关）1/1
node-4应用面docker compose 全栈：Traefik、ZITADEL、Casdoor、NATS、Temporal、Harbor1/2（keepalived VIP）
  • 最小生产 = 3 节点（etcd 三副本分布 node-1/2/3；应用面暂与 node-3 合署，标注重载）；标准 = 4 节点（应用面独立）。
  • Redis 由 Pigsty REDIS 模块部署（随 PGSQL 节点或独立 redis.yml 拓扑，v1 建议 1 主 1 复制挂 node-1/2）。

2.2 节点基础要求（P0 输入）

项要求
操作系统EL 8/9 或 Ubuntu 22/24（Pigsty 4.5 支持矩阵），x86_64
硬件数据节点：≥8C/32G，数据盘 NVMe/SSD 独立挂 /data（≥1T）；应用节点：≥8C/16G，系统盘 ≥200G
网络节点间内网互通（建议万兆或 ≥1G）、统一 VIP（keepalived，浮在 haproxy 前）、出网或离线仓库二选一
时钟chrony 与内网 NTP 源同步（偏差 >100ms 会影响复制与证书）
SSH管理机（node-3）到全部节点 root 免密（Ansible 前提）

四、安装编排（P0~P9）

映射 115 号 S 序：P0P1≈S0/S1，P2P3=S4（数据基座 Pigsty 形态），P4≈S2/S3，P5=入口（S3 壳），P6=S5，P7=S8，P8=S9，P9=S17 前段。启动正序、停止逆序纪律不变。

序步骤要点验收门禁

P2Pigsty 安装（数据面）node-3 上 get-pigsty（离线包）→ 编写 pigsty.yml：nodes[]=node-1/2/3、pg_cluster=opic-pg、pg_databases[]=[opicdb,zitadel,casdoor,temporal,temporal_visibility]、pg_users[]=各业务角色（见 §四.附）、启用 redis.yml 拓扑 → ansible-playbook pigsty.yml → ansible-playbook redis.ymlpatronictl list 全员 running/primary 唯一；curl node-VIP:5433（rw）与 :5434（ro）通；VIP ping 通；redis-cli -h <vip> PING；pgbackrest --stanza=pgsql check 通过
P3建库授权核对Pigsty 已声明式建库建角色；核对：库 5 个、属主角色与 .env.prod 口令一致、pg_hba.conf 仅放行应用网段（scram-sha-256），禁 trustpsql 逐库连接验证 + pg_hba_file_rules 审计无宽放行
P4应用节点前置node-4 安装 Docker 24+/Compose v2、建 opic-net、/opt/opic/{data,certs}、离线导入 compose 镜像 tar（ZITADEL/Casdoor/NATS/Temporal/Traefik 五栈，版本口径 = 117 号实测：ZITADEL ghcr v4.19.3、Temporal 1.29.0）docker info、docker load 清单核对、DNS 解析五个域名到 node-4
P5Traefik（TLS 入口）复用 stacks/traefik，生产差异：TRAEFIK_WEB_PORT=80、TRAEFIK_WEBSECURE_PORT=443、关闭 api.insecure、追加 --entrypoints.web.http.redirections.entrypoint.to=websecure、证书动态文件配置（通配符证书挂 /opt/opic/certs）https://auth.opic… 证书链通过；http:// 301 到 https；dashboard 无未授权访问
P6ZITADEL ＋ Casdoor复用 stacks/zero-trust/stacks/casdoor，生产差异：库 host=node-VIP（haproxy 5433）、ZITADEL_EXTERNALSECURE=true、ZITADEL_DOMAIN=auth.opic…、ZITADEL_EXTERNALPORT=443、Casdoor 走 casdoor.opic…（443）；login-client PAT / masterkey 流程同 DEV（volume chown init 容器保留）healthz 与 login 经 https 域名 200；ZITADEL 库在 Pigsty 实例（\l 可见且非容器）
P7NATS → TemporalNATS monitor 仅内网 DNS；Temporal：DB 指向 Pigsty VIP（库名/口令为 P2 声明值），auto-setup 迁移自身 schema（116 号 §3.2 豁免不变），admin-tools 1.30.4/jsz 无 error；operator cluster health OK；UI 经 https 域名可达
P8Harbor（v2.15.2）官方安装器（在线或离线 tgz），harbor.yml：https.port=8443 + 通配符证书、external_url=https://harbor.opic…、data_volume=/opt/opic/harbor/data（独立盘/NFS）；HARBOR_ADMIN_PASSWORD 走 .env.prodhttps://harbor.opic…/api/v2.0/health healthy；docker login + push/pull 演练一镜像
P9验证收口九项生产门禁（表下）＋ 两项演练：① patroni switchover 主备切换，应用连接无感知（haproxy 重路由 ≤10s）；② pgbackrest 恢复演练（restore 到临时目录 + PITR 校验）门禁脚本全绿 + 两项演练记录归档（117 号 verify-step1.sh 改造为生产版：PG 门禁指向 VIP:5433，其余同）

§四.附：Pigsty 声明式建库清单（写入 pigsty.yml）

建库规则（用户规则，2026-10-01）：OPIC 全部能力中心共用一个数据库实例 opicdb，每个能力中心为单独的一个 schema。第三方引擎（ZITADEL/Casdoor/Temporal）不属能力中心，因引擎限制（ZITADEL/Temporal 要求独占数据库命名空间）保留独立库——此为该规则的显式边界，随本方案登记。

库内容属主角色消费方
opicdb（唯一业务库）23 个中心 schema（每中心一个）：osec osys oarc odbs oreg ocrt ovpn oign oclc oosc oadd oast ousr opip oapp ocsc oapf oopr odat omdl oknb omon ocmp（域码小写）opicdb_owner（组角色；第二步各中心上线时按域发专属登录角色并授权对应 schema）23 个能力中心（中心内 migrations/ 纪律不变，禁跨 schema 外键，跨中心只走 API+Event Bus）
zitadel引擎自管 schemazitadelstacks/zero-trust（运维侧 IdP）
casdoor引擎自管表casdoorstacks/casdoor（租户侧 IdP）
temporal / temporal_visibility引擎自管 schematemporalstacks/temporal（standard visibility，无 ES）

对象策略恢复目标

六、安全基线（生产版，上线前逐项核对）

  1. 防火墙最小端口：node-1/2/3 仅放行节点间网段（5433/5434/8008 patroni/2379-2380 etcd/9100-9101 exporter/22 管理网）；node-4 对外仅 80/443/8443，22 限管理网；Pigsty Grafana(3000)/Prometheus(9090) 仅内网。
  2. pg_hba.conf：仅应用网段 + 管理网段，scram-sha-256，禁 trust；变更走变更单。
  3. Traefik api.insecure=false（DEV 坑位结论直接继承）；dashboard 如需开放走 BasicAuth + 内网 ACL。
  4. 全站 TLS：五域名证书链校验入月度巡检；证书到期前 30 天告警（O-MON 或 cron）。
  5. SSH：key-only、禁 root 密码、fail2ban；管理操作留 X-Trace-Id 习惯（平台规则第 8 条审计头）。
  6. .env.prod 与 masterkey：age 加密存放于堡垒/密码库；严禁入 git（.gitignore 已排除 .env*）。
  7. Casdoor/ZITADEL 管理员首登改密并轮换；Harbor admin 同。

七、监控与告警衔接

  • 采集面：Pigsty INFRA 自带 Prometheus/Grafana（PG/PGPool/Redis/节点 exporter），保留为本机采集（116 号 §三决策 5）。
  • 聚合面：O-MON（第二步）联邦采集上述 Prometheus；第一步期间用 Pigsty 内置告警最小集：复制延迟 >10s、WAL 堆积、磁盘 >85%、连接数 >80%、backup 失败、证书到期不足 30 天。
  • 门禁巡检：verify 脚本（生产版）进 crontab 每小时，异常 wall + 消息通道。

八、升级与回退

场景流程回退
Pigsty 小版本先 pgbackrest 全量 → ansible playbook 升级（先 replica 后 primary，switchover 滚动）按库 dump + 旧版本重装回退；或 PITR
PG 小版本同上滚动：switchover → 升 replica → 提主 → 升旧主Patroni 回切
应用面（compose）改 .env.prod tag → pull → 逆序 down → 正序 up（115 号 §6.3）tag 回退重部署
整体回退容器化模式DEV 形态即 fallback：应用栈指回容器 PG（dump/restore 迁移）116 号 §五

九、与 116/117 的关系

  • 116 号 §三决策 1（两分法）在本方案完整落地；§4.1 决策（Temporal 并库）随 P2 声明式建库一并关闭。
  • 117 号 DEV 实测结论继续适用于生产应用面：traefik label 挂目标容器、zitadel 不设 healthcheck（post-install 门禁）、init-perms 卷属主、casdoor dbName 与去 --createDatabase、nats 无服务器级 max_streams、镜像 tag 前缀（ghcr 带 v）与 --platform linux/amd64 搬运。
  • 数据迁移（DEV → 生产，如需）：dumpall 全量 + 角色口令对齐 .env.prod；不做在线复制。

11.2 生产档配置基线（192.168.3.200）

  • 部署根 /opt/opic-prod（.env 即 .env.prod，600）；数据 /opt/opic/{database,redis,harbor,nats,temporal}；备份 /opt/opic-backup（cron 每日 02:00，保留 14 天，首次备份已验证）。
  • 端口（11.1b 后定版）：Traefik 80(http,301→https)/443(https)；dashboard 127.0.0.1:18887（仅本机）；子域路由：auth. / casdoor. / temporal. / nats.opic-ai.ccoe.tech（均 443）；直连 fallback 口保留：casdoor 18001、nats 14222/8222、temporal 7233/8233、harbor 18700、pg 127.0.0.1:15432、redis 127.0.0.1:26379、zitadel break-glass 127.0.0.1:18082。
  • 域名（规则定版）：*.opic-ai.ccoe.tech → 192.168.3.200；入口 https://auth.opic-ai.ccoe.tech:19443（ZITADEL issuer）。后续中心接入即按 casdoor./harbor./nats./temporal.opic-ai.ccoe.tech 子域规划（现经 IP 直连端口，收编 Traefik 随企业证书）。
  • 建库（§四.附规则已生效）：opicdb + 23 中心 schema（opicdb_owner 属主，门禁校验）＋ zitadel/casdoor 独立库 + temporal 栈内库。
  • 凭据：唯一事实源 /opt/opic-prod/.env；DEV 时代凭据已随环境销毁（备份归档于工作区 output/credentials-archive/，仅本机）。

11.3 扩容触发条件（单机 → 集群）

以下任一发生即启动 §二 标准拓扑迁移：① prd-env 网络恢复；② 中心开始上量（并发/存储水位 >60%）；③ 出现可用性 SLA 要求。迁移 = pg_dumpall → Pigsty HA 导入 → 应用面改 PG_HOST → 按门禁复验。

本文件为生产形态部署方案的 v1.0 基线；单机生产档已于 2026-10-01 落地（§十一）；标准多节点拓扑待 prd-env/专用机就位后按 §二 回填执行；变更走 116/118 台账追加。
